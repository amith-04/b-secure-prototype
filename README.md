# B-Secure

A pre-publication brand governance tool that evaluates marketing content against approved brand rules and factual specifications, explains findings with evidence citations, and ensures human decision-makers retain ultimate approval authority.

---

## 1. Project Overview & Problem Statement

### Problem
Content generated by employees, external agencies, and AI tools frequently drifts from approved brand guidelines, introduces unsupported claims, or misrepresents product specifications. Reviewing drafts manually across scattered guideline documents is slow and inconsistent, while fully automated AI publishing introduces severe hallucination and compliance risks.

### Solution
B-Secure provides a structured, human-in-the-loop review workflow. It evaluates drafts using a hybrid model: deterministic client-side rules catch prohibited terms and missing disclaimers immediately, while contextual AI analysis checks factual claims against approved brand specifications. Findings are linked directly to evidence, unverified statements are marked for human verification rather than definitively declared false, and human managers retain final sign-off with mandatory audit logging for policy overrides.

## 3. Implemented Features

- **Hybrid Compliance Checking:**
  - **Deterministic Rule Checks (`ruleCheck`):** Instant regex-based client checks for prohibited phrases (e.g., medical claims, superlatives) and required contextual disclaimers (e.g., battery life disclosures).
  - **Contextual AI Analysis (`api/check.js`):** Serverless evaluation powered by Groq Cloud, checking nuanced factual claims against approved brand specifications.
- **Evidence-Linked Findings:**
  - Every finding highlights the exact matched text, assigns a severity (`Low`, `Medium`, `High`), explains the issue, and references the specific brand rule ID and source document.
  - Where a claim cannot be verified against approved specifications, it is classified as `Needs verification` with no fabricated rule ID.
- **Intent-Preserving Rewrites:**
  - When issues are identified, the AI proposes an alternative draft that corrects the violation while preserving the author's original intent. Creators can insert the rewrite into their draft with one click.
- **Role-Based Review Workflow (Simulated):**
  - **Creator:** Draft checking, evidence inspection, one-click rewrite insertion, draft submission, tracking in "My submissions", and revision/resubmission of rejected or returned copy.
  - **Manager:** Review queue prioritized by auto-escalation flags and calculated risk scores (0–100), detailed finding reviews, split view of pending and decided drafts, and decision actions (**Approve**, **Request changes**, **Reject**). Mandatory documented override reasons are enforced when approving content with unresolved flags.
  - **Admin:** Brand rule management (add, activate/deactivate, delete rules across phrase, required, and fact types), AI policy controls (strictness configuration: `lenient`, `balanced`, `strict`; AI toggle; escalation toggle), permissions matrix, and audit log inspection.
- **Insights Dashboard (Manager & Admin):**
  - Aggregates operational metrics across all submissions: Total Submissions, Pending, Approved, and Rule vs. AI findings count.
  - Generates a ranked distribution chart of recurring issue categories with visual proportion tracks.
- **Local Persistence & Audit Trail:**
  - Active brand rules, submitted drafts, review histories, and policy changes persist in the browser via `localStorage` (key: `bsecure-demo-v1`).
  - A chronological audit log tracks all administrative and managerial actions with a reset option.
- **Interactive Sample Scenarios:**
  - Four pre-configured test drafts demonstrating compliant, violating, unsupported, and mixed-issue content.

## 4. End-to-End Workflow

1. **Draft Submission & Checking (Creator):**
   - The creator enters draft copy (or selects a sample scenario) and clicks **Check content**.
   - Deterministic rules run instantly in the browser; simultaneously, `/api/check` forwards the text and active guidelines to Groq for contextual analysis.
2. **Reviewing Findings & Revision (Creator):**
   - The creator reviews color-coded findings. They may manually edit the draft, adopt the AI-suggested rewrite, or click **Submit for manager review**.
3. **Queue Prioritization & Evaluation (Manager):**
   - Submitted drafts appear in the manager's **Review queue**. If the draft contains high-severity or unverified findings and escalation is enabled, it is automatically escalated to the top of the queue.
   - The manager opens the submission to inspect the draft alongside all flagged findings, risk scores, and source evidence.
4. **Decision & Documented Override (Manager):**
   - The manager can **Approve**, **Request changes**, or **Reject**.
   - If a manager approves content that contains unresolved findings, the system requires a written override justification before the decision can be recorded.
5. **Revision Cycle (Creator):**
   - If changes are requested or rejected, the creator views the manager's feedback under **My submissions** and clicks **Revise and resubmit**, preserving submission history.
6. **Governance & Audit (Admin):**
   - All role actions, setting adjustments, and approval decisions (including override rationales) are committed to the **Audit log**.
   - Admins can add or toggle rules, adjust AI strictness levels, and monitor aggregate trends in **Insights**.

## 5. Technology Stack & Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                    Browser Client (SPA)                     │
│  - Vanilla HTML5 / CSS3 / ES6+ JavaScript (Zero-build)       │
│  - Client-Side Regex Rule Engine (ruleCheck)                │
│  - State & Audit Log Persistence (localStorage)             │
│  - Role Simulation Switcher (Creator / Manager / Admin)     │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               │ HTTPS POST /api/check
                               ▼
┌─────────────────────────────────────────────────────────────┐
│           Vercel Serverless Function (Node.js)              │
│  - Active endpoint: api/check.js                            │
│  - Configured via vercel.json: Memory 256 MB, Max 30s       │
│  - Sliding-Window In-Memory Rate Limiter (8 req/min/IP)     │
│  - Origin Header Validation (Anti-CSRF)                     │
│  - Input Sanitization & Length Guardrails (1-2000 chars)     │
│  - 25s AbortController Timeout Protection                   │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               │ HTTPS POST (Bearer GROQ_API_KEY)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                      Groq Cloud API                         │
│  - Endpoint: https://api.groq.com/openai/v1/chat/completions │
│  - Model: process.env.GROQ_MODEL || 'openai/gpt-oss-120b'   │
│  - Temperature: 0.2 | Format: json_object                   │
└─────────────────────────────────────────────────────────────┘
```

- **Frontend:** Pure HTML5, Vanilla CSS3 (custom properties, responsive layouts, inline SVGs), and modern ES6+ JavaScript. No build step, bundlers, or third-party frontend dependencies.
- **Backend:** Node.js serverless function (`api/check.js`) hosted on Vercel. *(Note: The repository also contains a legacy root `check.js` from earlier experimentation; Vercel executes only `api/check.js`)*.
- **AI Inference Provider:** Groq Cloud API using OpenAI-compatible chat completions.
- **Client Storage:** Web Storage API (`localStorage` key: `bsecure-demo-v1`).

### Exploring the Application
1. Open the [Live Demo](https://b-secure-prototype.vercel.app/).
2. Select a role from the role selector:
   - **Creator:** Choose a sample draft from the buttons, click **Check content**, review the findings, and click **Submit for manager review**.

### Built-In Test Scenarios (AquaPulse Fictional Brand)
- **Clean draft:** Contains fully compliant specifications (750 ml, BPA-free, up to 14 days battery, IP67 splash-proof, with disclaimer). Demonstrates zero false positives and a risk score of 0.
- **Rule violations:** Contains medical claims ("cure dehydration") and absolute guarantees ("guaranteed 100% safe"). Caught immediately by deterministic rule patterns.
- **Unsupported claims:** Claims the bottle can be used for "scuba diving" and is "dishwasher safe" (contradicting the IP67 brief immersion limit and hand-wash spec). Flagged by AI contextual analysis.
- **Mixed issues:** Misspells the product name as "Aqua Pulse", makes an unsupported 30-day battery claim, and makes a disparaging comparison against competitor "HydroSmart". Demonstrates multiple simultaneous triggers.

## 7. Local Setup Instructions

Because B-Secure is a zero-build project, no build commands (e.g., `npm build` or `vite build`) or package installations are required.

### Prerequisites
- [Node.js](https://nodejs.org/) (v18.0.0 or higher recommended)
- [Vercel CLI](https://vercel.com/docs/cli) (`npm install -g vercel` or using `npx vercel`)

### Setup Steps
1. Clone the repository:
   ```bash
   git clone https://github.com/amith-04/b-secure-prototype.git
   cd b-secure-prototype
   ```
2. Create a `.env` file in the project root:
   ```env
   GROQ_API_KEY=gsk_your_actual_groq_api_key_here
   # Optional: specify model (defaults to openai/gpt-oss-120b in api/check.js if omitted)
   GROQ_MODEL=llama-3.3-70b-versatile
   ```
3. Start the local development environment using Vercel CLI:
   ```bash
   npx vercel dev
   ```
4. Open `http://localhost:3000` in your browser.

*(Note: Running `index.html` via a generic static file server will load the UI, but AI checks require running via `vercel dev` so the `/api/check` serverless function can execute).*

1. Push this repository to GitHub.
2. In the Vercel Dashboard, select **Add New Project** and import the repository.
3. In **Build and Output Settings**, leave Framework Preset as **Other** (no build command or output directory needed).

## 9. Transparency, Limitations & Privacy

- **Nature of AI Analysis:** AI-assisted analysis is advisory and probabilistic. It can generate false positives, misinterpret creative metaphors, or overlook subtle issues. It is designed to assist human judgment, not replace it.
- **Definition of Evidence:** The application evaluates drafts solely against the rules and factual specifications actively configured in the tool. It does **not** conduct autonomous web searches or independent external fact-checking. A status of `Needs verification` indicates that a claim cannot be verified against currently approved brand rules—it does **not** prove the claim is factually false.
- **Data Transmission & Privacy:**
  - When AI checking is executed, the draft text, active rule definitions, and previous rule matches are transmitted over HTTPS to Groq Cloud for inference.
  - The serverless function does not log draft copy or user identifiers.
  - No client-side trackers, analytics cookies, or external CDN scripts are loaded.
- **Storage Boundaries:** All drafts, custom rules, audit records, and submission states exist solely in the individual browser's `localStorage`. Data is not shared across devices or browser sessions.
- **Rate Limiting Scope:** The rate limiter (8 requests per minute per IP) uses an ephemeral in-memory Map within the serverless function container. It provides best-effort burst protection, but counters reset when serverless instances cold-start.
- **Role Simulation:** The role switcher is a demonstration UI state machine. It does not provide authenticated access control or cryptographic authorization.

## 10. Security Considerations

- **Server-Side Credential Protection:** The Groq API key is stored exclusively as an environment variable in the serverless execution environment and is never exposed to the client browser.
- **Anti-CSRF Origin Verification:** The `/api/check` handler checks `req.headers.origin` against `req.headers.host`, returning HTTP 403 Forbidden for cross-origin requests.
- **Input Sanitization & Length Guardrails:** Draft content is restricted to 1–2,000 characters. Input arrays (rules and found items) are truncated to 30 items maximum to prevent denial-of-service and payload-stuffing attacks.
- **Prompt Injection Mitigations:** System instructions explicitly isolate draft content within delimited boundaries (`"""DRAFT"""`) and mandate that content be evaluated strictly as data, never executed as instructions.
- **Strict Output Parsing:** Model output is coerced to strict JSON format (`response_format: { type: 'json_object' }`), and fields are validated and sanitised before returning them to the client.

## 11. Future Work

The following items were identified during prototype planning and are planned for future development:
- **Authentication & Multi-Tenancy:** Real authentication (e.g., Supabase Auth or OAuth 2.0) with organization-level access control.
- **Shared Persistent Storage:** Centralized database storage (e.g., PostgreSQL) replacing client `localStorage` to enable real-time collaboration between creators and managers.
- **Durable Distributed Rate Limiting:** Redis-backed rate limiting (e.g., Upstash) across serverless instances.
- **Multimodal & Asset Checking:** Extending governance checks to marketing imagery, slide decks, and document uploads (PDF/DOCX).
- **External Knowledge Base Integrations:** Bi-directional synchronization with enterprise guideline repositories (Notion, Google Docs, Confluence).
